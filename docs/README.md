## Architecture decisions

Important technical decisions are recorded as lightweight ADRs in
[`adr/`](./adr/). Each entry documents the problem, the decision, the
alternatives considered, and the consequences.

| ADR                                      | Decision                                |
| ---------------------------------------- | --------------------------------------- |
| [0001 — Development toolchain](./adr/0001-development-toolchain.md) | Bun workspaces, strict TypeScript, ESLint + Prettier, Vitest, GitHub Actions CI. |
| [0002 — Phase 1 application foundation](./adr/0002-phase-1-application-foundation.md) | `db` / `auth` / `api` packages, evolvable schema, scrypt credentials, opaque sessions, server-side workspace authorization. |
| [0003 — Business Brain](./adr/0003-business-brain.md) | `@dealora/brain` domain, single canonical company record, six workspace-scoped tables, additive migration, claim-approval safety, agent-facing `getBusinessContext`. |
| [0004 — Revenue Goal Engine](./adr/0004-revenue-goal-engine.md) | `@dealora/goal` domain, structured goal fields, provenance (explicit/inferred/assumption/unknown), deterministic replaceable `GoalParser`, validated lifecycle transitions, Business Brain references, goal history. |
| [0005 — Revenue Plan Compiler](./adr/0005-revenue-plan-compiler.md) | `@dealora/plan` domain, eleven typed strategy sections, statement provenance (fact/inference/assumption/recommendation/unknown), deterministic replaceable compiler, goal preconditions, per-goal versioning, plan approval separated from action approval. |
| [0006 — Account & Prospect Input](./adr/0006-account-prospect-input.md) | `@dealora/account` domain, input-not-evidence provenance (`manual`/`csv`/`approved_integration`), deterministic deduplication (normalized domain; account + normalized email), ambiguity preserved rather than merged, row-level CSV import with a per-row result, soft archive cascading to contacts, optional validated plan association. |
| [0007 — Research Engine](./adr/0007-research-engine.md) | `@dealora/research` domain, research requests over existing accounts, minimal `pending`/`running`/`completed`/`failed`/`cancelled` lifecycle, `ResearchProvider` boundary restricted to permitted sources (no scraping bypass), research findings that are **not** evidence, explicit `fact`/`inference`/`hypothesis`/`recommendation` labels, provenance and freshness bands, idempotent creation and retry, failures recorded rather than swallowed. |
| [0008 — Evidence System](./adr/0008-evidence-system.md) | `@dealora/evidence` domain, `account_claims` + `evidence` (schema v7), research finding / evidence / claim kept distinct, one controlled finding→evidence conversion, `AccountClaim` kept separate from the Business Brain `Claim`, verbatim source attribution with no invented citations, Phase 6 confidence/freshness/relevance bands reused unchanged, contradiction represented and never resolved, caller-directed supersession, status-only history that never deletes, no qualification and no score. |
| [0009 — Qualification Engine](./adr/0009-qualification-engine.md) | `@dealora/qualification` domain, `qualifications` (schema v8), the roadmap's five dimensions and ten explicit criteria read from the canonical ICP and the Revenue Goal window, deterministic scoring with stored rule version and context digest, every score carrying reason / evidence / confidence, `insufficient_data` for missing evidence and `contested` for conflicting sources with no score in either case, immutable versioned evaluations, a criteria inspector exposed before any account is scored, no lifecycle, no outreach and no approval. |
| [0010 — Approval Engine](./adr/0010-approval-engine.md) | `@dealora/approval` domain, `approval_requests` + `approval_request_events` (schema v10), an approval bound to one **exact** immutable draft version plus a `preview_digest` of the exact previewed content that is re-derived at decision time, server-derived reviewer identity and instant enforced in both the service and storage, one `approved` state reachable only by explicit human decision (never by score, threshold or timer), `changes_requested`/`cancelled`/`expired` as closures that authorize nothing, reasons required for refusals, append-only audit trail, a refusals-and-previews inspector, and **no execute route**. |
| [0011 — First Outbound Integration](./adr/0011-first-outbound-integration.md) | `@dealora/outbound` domain, `outbound_actions` + `outbound_events` + `outbound_suppressions` (schema v11), exactly one channel behind a narrow `OutboundProvider` interface, a sixteen-check verification chain re-derived from stored rows on **every** send rather than trusted from staging, `sent` writable from exactly one place and CHECK-constrained to a provider confirmation, failures recorded with closed codes and never a `sentAt`, two-level idempotency (one action per approval, provider-side de-duplication on a stable key), explicit capped retries with no loop, permanent attributed opt-out suppression checked before the provider is resolved, no scheduler or queue, and an honestly declared sandbox provider that performs no network I/O. |
| [0012 — Conversation Engine](./adr/0012-conversation-engine.md) | `@dealora/conversation` domain, `inbound_messages` + `conversation_classifications` + `conversation_events` (schema v12), the ten states `DEALORA_BLUEPRINT.md` §18 names as a closed vocabulary, a deterministic rules classifier with a stored version (no model, no clock, no randomness), safety precedence so an opt-out and a refusal outrank a question asked in the same breath, explicit negation handling so `not interested` is never read as interest, `unknown` with no guess when nothing matches, `humanInterventionRequired` true for everything except an opt-out (both CHECK-constrained in the schema and re-checked in the store), an opt-out honoured immediately by writing to the **existing** Phase 11 suppression list, one classification per message, a closed vocabulary of four *recommendations* of which none is "send a reply", and — the negative space — no sender, no approver, no scheduler, and no path from a reply to evidence. |
| [0013 — Meeting Workflow](./adr/0013-meeting-workflow.md) | `@dealora/meeting` domain, `meetings` + `meeting_briefs` + `meeting_events` (schema v13), a seven-state booking machine in which `DEALORA_BLUEPRINT.md` §17's Level 2 rule ("schedule event" requires approval) is structural — `recommended → booked` and `awaiting_approval → booked` do not exist as transitions, so no single call can book a meeting, a person's approval walks `awaiting_approval` on the way and records both steps, and `cancelled` is terminal so a replay cannot resurrect a withdrawn booking. A meeting must point at a Phase 12 classification read as `positive_intent`/`interested` **and** a Phase 8 qualification in state `qualified`, both re-derived in storage rather than trusted from a caller; one response yields at most one meeting. The approval is digest-bound and re-derived at decision time exactly as Phase 10 does, with the approver taken from the session in both the service and the store. `ROADMAP.md` §30 puts calendar and CRM in Phase 23, so the shipped `MeetingCalendarProvider` is a sandbox that performs no network I/O and `booked` is written only on a provider confirmation. The opt-out list is re-checked at proposal, at approval **and** at booking. §22's brief is assembled from stored records, references claims and evidence by id, and names every gap rather than filling it. And the negative space: no scheduler, no invitation, no live calendar, no CRM, and no path from a meeting to evidence. |
| [0014 — Next Best Action Engine](./adr/0014-next-best-action-engine.md) | `@dealora/nextaction` domain, `next_best_actions` (schema v14), eighteen reachable revenue states declared once as `[state, action]` pairs with every published vocabulary *derived* from that one table, and `approval_required` CHECK-constrained to agree with `DEALORA_BLUEPRINT.md` §17's risk level — so "does a person have to act first?" is a property of the row rather than something a client may assert. The live answer is recomputed from current rows on every read (the stored row is a *history of advice*, so a stale "send this now" can never be served), and the engine is a pure function: no clock, no randomness, no model, no network. Every recommendation carries all seven of `ROADMAP.md` §21's required fields as fields rather than prose, and confidence is ADR 0009's weakest **band** — the `93%` in the Blueprint is treated as a display illustration because this repository has no calibration data from which a number could mean anything. Safety is the first branch, so a suppressed address can never come back with a recommendation to contact it, and a cancelled meeting is not re-proposed over. `level_3_high_impact` is deliberately absent. And the negative space, which is the point: no sender, no approver, no calendar, no scheduler, no network I/O, no provider seam, no path from a recommendation to the Phase 7 evidence graph, and a single account id as the entire client input surface. |

## Conventions

- Phase status and the next required slice are tracked in `ROADMAP.md`;
  update the roadmap when a phase gate is met.
- New environment keys are documented in `CONTRIBUTING.md` as they are
  introduced by the corresponding phase; secrets are never committed.
- Phase status is summarized in `README.md`; when a phase gate is met, update
  both so the roadmap and the overview agree.
- Public module interfaces carry doc comments; decisions that shape the
  architecture get an ADR.
