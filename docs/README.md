## Architecture decisions

Important technical decisions are recorded as lightweight ADRs in
[`adr/`](./adr/). Each entry documents the problem, the decision, the
alternatives considered, and the consequences.

| [0009 — Qualification Engine](./adr/0009-qualification-engine.md) | `@dealora/qualification` domain, `qualifications` (schema v8), the roadmap's five dimensions and ten explicit criteria read from the canonical ICP and the Revenue Goal window, deterministic scoring with stored rule version and context digest, every score carrying reason / evidence / confidence, `insufficient_data` for missing evidence and `contested` for conflicting sources with no score in either case, immutable versioned evaluations, a criteria inspector exposed before any account is scored, no lifecycle, no outreach and no approval. |
| [0010 — Approval Engine](./adr/0010-approval-engine.md) | `@dealora/approval` domain, `approval_requests` + `approval_request_events` (schema v10), an approval bound to one **exact** immutable draft version plus a `preview_digest` of the exact previewed content that is re-derived at decision time, server-derived reviewer identity and instant enforced in both the service and storage, one `approved` state reachable only by explicit human decision (never by score, threshold or timer), `changes_requested`/`cancelled`/`expired` as closures that authorize nothing, reasons required for refusals, append-only audit trail, a refusals-and-previews inspector, and **no execute route**. |
| [0011 — First Outbound Integration](./adr/0011-first-outbound-integration.md) | `@dealora/outbound` domain, `outbound_actions` + `outbound_events` + `outbound_suppressions` (schema v11), exactly one channel behind a narrow `OutboundProvider` interface, a sixteen-check verification chain re-derived from stored rows on **every** send rather than trusted from staging, `sent` writable from exactly one place and CHECK-constrained to a provider confirmation, failures recorded with closed codes and never a `sentAt`, two-level idempotency (one action per approval, provider-side de-duplication on a stable key), explicit capped retries with no loop, permanent attributed opt-out suppression checked before the provider is resolved, no scheduler or queue, and an honestly declared sandbox provider that performs no network I/O. |
| [0012 — Conversation Engine](./adr/0012-conversation-engine.md) | `@dealora/conversation` domain, `inbound_messages` + `conversation_classifications` + `conversation_events` (schema v12), the ten states `DEALORA_BLUEPRINT.md` §18 names as a closed vocabulary, a deterministic rules classifier with a stored version (no model, no clock, no randomness), safety precedence so an opt-out and a refusal outrank a question asked in the same breath, explicit negation handling so `not interested` is never read as interest, `unknown` with no guess when nothing matches, `humanInterventionRequired` true for everything except an opt-out (both CHECK-constrained in the schema and re-checked in the store), an opt-out honoured immediately by writing to the **existing** Phase 11 suppression list, one classification per message, a closed vocabulary of four *recommendations* of which none is "send a reply", and — the negative space — no sender, no approver, no scheduler, and no path from a reply to evidence. |
| [0013 — Meeting Workflow](./adr/0013-meeting-workflow.md) | `@dealora/meeting` domain, `meetings` + `meeting_briefs` + `meeting_events` (schema v13), a seven-state booking machine in which `DEALORA_BLUEPRINT.md` §17's Level 2 rule ("schedule event" requires approval) is structural — `recommended → booked` and `awaiting_approval → booked` do not exist as transitions, so no single call can book a meeting, a person's approval walks `awaiting_approval` on the way and records both steps, and `cancelled` is terminal so a replay cannot resurrect a withdrawn booking. A meeting must point at a Phase 12 classification read as `positive_intent`/`interested` **and** a Phase 8 qualification in state `qualified`, both re-derived in storage rather than trusted from a caller; one response yields at most one meeting. The approval is digest-bound and re-derived at decision time exactly as Phase 10 does, with the approver taken from the session in both the service and the store. `ROADMAP.md` §30 puts calendar and CRM in Phase 23, so the shipped `MeetingCalendarProvider` is a sandbox that performs no network I/O and `booked` is written only on a provider confirmation. The opt-out list is re-checked at proposal, at approval **and** at booking. §22's brief is assembled from stored records, references claims and evidence by id, and names every gap rather than filling it. And the negative space: no scheduler, no invitation, no live calendar, no CRM, and no path from a meeting to evidence. |
| [0014 — Next Best Action Engine](./adr/0014-next-best-action-engine.md) | `@dealora/nextaction` domain, `next_best_actions` (schema v14), eighteen reachable revenue states declared once as `[state, action]` pairs with every published vocabulary *derived* from that one table, and `approval_required` CHECK-constrained to agree with `DEALORA_BLUEPRINT.md` §17's risk level — so "does a person have to act first?" is a property of the row rather than something a client may assert. The live answer is recomputed from current rows on every read (the stored row is a *history of advice*, so a stale "send this now" can never be served), and the engine is a pure function: no clock, no randomness, no model, no network. Every recommendation carries all seven of `ROADMAP.md` §21's required fields as fields rather than prose, and confidence is ADR 0009's weakest **band** — the `93%` in the Blueprint is treated as a display illustration because this repository has no calibration data from which a number could mean anything. Safety is the first branch, so a suppressed address can never come back with a recommendation to contact it, and a cancelled meeting is not re-proposed over. `level_3_high_impact` is deliberately absent. And the negative space, which is the point: no sender, no approver, no calendar, no scheduler, no network I/O, no provider seam, no path from a recommendation to the Phase 7 evidence graph, and a single account id as the entire client input surface. |
| [0015 — Revenue Graph](./adr/0015-revenue-graph.md) | `@dealora/revenuegraph` domain, **no tables and no migration** (schema stays v14): the twelve `ROADMAP.md` §22 relationships are *derived on read* from the rows Phases 5–13 store, published as a partition of seven node kinds (company, person, signal, evidence, opportunity, conversation, meeting) plus five refusals with reasons and owning phases (campaign, customer, revenue, agent, workflow). The opportunity node is the account's newest `qualified` qualification — its own id, never a new row — so a contested downgrade removes it and its edges from the next read. Every edge carries `derivedFrom` naming the exact rows the rule read (target row last), ordering is a total order so identical rows print the identical graph (`revenue-graph-1.0.0`), and an unreadable vocabulary refuses the read rather than publishing a half-understood account. Input is one account id, forged graph fields in the body are ignored, a workspace above 100 accounts is refused rather than truncated, and the surface is `authorize` alone — no writer, no actor, no recommender, no network I/O of any kind. |
| [0016 — Cost Engine](./adr/0016-cost-engine.md) | `@dealora/cost` domain, `cost_events` (schema v15): `ROADMAP.md` §23's six categories are an append-only, workspace-scoped fact attributed server-side to the session and to a **real execution of the same workspace** (`research_run`, `outbound_send`, `meeting_booking`; `workflow` refused by name with Phase 24 as its owner). Every total, average and ratio is *derived on read* — there is no stored aggregate, so nothing can go stale or double count. Money is whole minor units with exact `BigInt` division reported next to its remainder (naive `Math.floor` is pinned as off-by-one at the safe-integer boundary), one currency per workspace fixed by the first fact, and an overflowing total refuses the answer rather than rounding it. A measurement supersedes its own estimate per (execution, category), disclosed in `supersededEstimateMinor` rather than added twice; replays return the same fact, a reused key conflicts, forged `createdBy`/`workspaceId`/`totalMinor` body fields are ignored, and the six §23 metrics ship as a partition — three derived (cost per prospect, qualified opportunity, meeting) plus three refused with owning phases (customer → 17/23, revenue ratios → 17). No refund vocabulary, no scheduler, no provider, no network I/O. |
| [0017 — Revenue Dashboard](./adr/0017-revenue-dashboard.md) | `@dealora/dashboard` domain, **no tables and no migration** (schema stays v15): `ROADMAP.md` §24's twelve tiles plus the two `DEALORA_BLUEPRINT.md` §35 needs are *derived on read* from the rows Phases 3 and 5–16 store, so the dashboard cannot go stale or drift from the loop. Every tile is `derived` (a zero is a fact), `conditional` (the Revenue Goal needs an *active* goal, so an empty list answers `no_data`), or `no_data` with a reason and an owning phase — Direct Revenue, Pipeline Created and Customers are refused and name **Phase 23**, because `$0 pipeline` would be a financial claim nobody recorded. Outcomes and activity are computed from deliberately different sources: Qualified Prospects is accounts whose *newest* qualification is `qualified` (ADR 0015/0016's rule), an Opportunity also requires a meeting that reached a calendar (`booked`/`held`/`no_show`), and Agent Activity reports the work, so the gap between what was done and what it produced stays visible. Account-based counts are over sets, so double counting is impossible by construction; ordering inside a tile is a declared closed order or the store's own, with `createdAt`-then-`id` breaking the goal tie, so identical rows print byte-identical JSON (`dashboard-1.0.0`). The cost tile and the next-action tile are embedded **whole** from Phase 16 and Phase 14 through their own boundaries, so neither number nor advice has a second definition; "positive" is read from Phase 13's `MEETABLE_INTENTS` rather than re-declared. The policy route publishes the fourteen tiles, the three refusals and the four questions as an exact partition. Forged tile numbers, `userId` and `workspaceId` in a body are ignored, every read is workspace-scoped with the session's identity, and the surface is `authorize` plus nine `list*` calls — no writer, no actor, no recommender, no scheduler, no network I/O. |
| [0018 — Agent System](./adr/0018-agent-system.md) | `@dealora/agent` domain, `agent_registry` + `agent_registry_events` (schema v16): `ROADMAP.md` §25's **twelve agents** are declared in one versioned rule table carrying all twelve required fields (eleven in the declaration; the twelfth, `Status`, is the per-workspace row) alongside `DEALORA_BLUEPRINT.md` §30's `owner` and `model`, and a workspace stores **only the lifecycle state it decided** — a declaration is code, so the table can never drift from it or become a second source of truth. The **seven** states run on a published transition table with no `draft → production` shortcut, no transition into `draft`, and a terminal `archived`; `approved → production` is published but **gated**, and Phase 18 refused it outright naming **Phase 19** as its owner, because §26 gates production on evaluation evidence that did not exist yet (Phase 19 replaces the refusal with the real evidence gate — see 0019). `usableStates` is therefore **empty**: no agent can be used in any state, and nothing executes — there is no runner, dispatcher, tool invoker or model client anywhere in the package, and every declaration's `model` is `null`. Each of the 18 tools names the **phase that executes it**, so an agent holding `send_message` has still sent nothing (Phase 10 approval and Phase 11 suppression are untouched); `approvalImplied` is true for exactly `request_approval`, `send_message` and `book_meeting` — not `write_evidence`, which needs provenance (Phase 7) rather than a human. The `write_external` permission is published and granted to **nobody**. All 13 evaluation metrics are declared and owned by Phase 19; the 8 memory layers are declared and never opened. The event trail records **governance decisions only** — no run, no latency, no tool call — because §27 (Phase 20) owns traces. `CHECK` constraints pin both columns to the published vocabularies so a refused row is unrepresentable, `UNIQUE(workspace, agent)` keeps the registry a decision log rather than a history, and migration v16 adds two empty tables while rewriting nothing. The registry prints in a constant total order and the trail sorts newest-first with a **stable sort and no id tiebreak**, so same-millisecond decisions read in the order they were made rather than by a random id. Client-supplied `updatedBy`, `createdAt`, `workspaceId`, `actorUserId` and `kind` are ignored; the target state is the only value a request contributes. Five workspace-scoped routes; `UNAVAILABLE` maps to a generic `SERVER_ERROR`. |
| [0019 — Agent Evaluation](./adr/0019-agent-evaluation.md) | `@dealora/evaluation` domain, `agent_evaluation_runs` + `agent_evaluation_observations` (schema v17): `ROADMAP.md` §26's **thirteen metrics** are published in one versioned rule table (`evaluation-1.0.0`) with a kind, direction, threshold, minimum sample and stated rationale each — rates in exact integer basis points compared by cross-multiplication, never by float division, so "exactly at the threshold" is a decidable fact. Human judgement in, deterministic measurement out: a caller contributes a **subject** and either one of three verdicts (`met` / `unmet` / `unobserved`) or a whole-number measurement, and the engine derives every rate, total, threshold comparison and the gate itself. `unobserved` stays in the denominator, so declining to judge can only lower a metric. Below `minimumSample` a metric is `insufficient_evidence` with `measured: null` — absence is reported, never zero-filled. `cost`'s bar is the agent's **own** declared `costLimits` read from `@dealora/agent` (one number, one owner; total *and* per-execution both checked), and `latency` is the **slowest** recorded run against Phase 19's own published `LATENCY_CEILING_MS` — a product judgement, said plainly rather than presented as a roadmap constant. Evidence is keyed by `(workspace, agent, version)`: a round pins the declared version, so a new version starts with no evidence by construction, and a fresh round **supersedes** rather than edits, so nothing is ever updated or deleted. No derivation consults a clock, and no column stores a rate, a pass or a status — asserted against the DDL. Phase 18's unconditional `approved → production` refusal becomes `AGENT_GATED_TRANSITIONS`: the edge stays published and `decideTransition` is **fail-closed** (no gate wired ⇒ the Phase 18 refusal verbatim, naming Phase 19), while a satisfied gate is derived from stored rows on every call and a storage outage resolves to *refused*. The gate grants a governance state and **no capability**: `usableStates` stays `[]` and `usable` stays `false`, because nothing in this repository runs an agent. `DEALORA_BLUEPRINT.md` §27 (Phase 20) still owns run traces, token usage and tool calls, and this phase writes none. Five workspace-scoped routes; a forged `workspaceId`, `createdBy`, `createdAt`, version, rate or status in a body is ignored and answered byte-identically. |
| [0020 — Agent Trace & Observability](./adr/0020-agent-trace-observability.md) | `@dealora/trace` domain, `agent_trace_runs` + `agent_trace_events` (schema v18): `ROADMAP.md` §27's chain is published as **seven** stages in the roadmap's own order (agent, decision, tool_call, evidence, result, approval, external_action), and that order is the trail's sort key, so a stage with no steps reads as a tally of zero rather than being absent. §27's **nine** tracked dimensions are each derived from real stored facts — the **slowest** step rather than a sum (steps in one run may overlap), reported model/token usage never estimated, tool names read from `@dealora/agent`'s eighteen declarations rather than restated, errors counted, **retries** read from storage's `attempt` counter, and cost attributed through **Phase 16's own** `cost_events` under one new `agent_run` execution kind (no second cost table, no second total, `null` rather than a fabricated zero). §27's critical rule is **structural, not conventional**: `TraceRunStatus` has five members and *no request can supply one* — the close route carries a run id and does not read its body at all — the status is derived in storage from the recorded outcomes, and a fifth value `unverified` makes closing an empty trace incapable of producing a success. `unknown` is a first-class outcome, so an external action nobody confirmed is never reported as a delivery or a failure; `DEALORA_BLUEPRINT.md` §70's failure→retry→alternative→degradation→escalation chain is representable because each is a separate step, not a flag. The rule is deliberately **duplicated**: storage derives on write and the domain re-derives on read, and a closed run whose two derivations disagree is refused with `UNAVAILABLE` rather than printed. Ordering is server-derived because `recordedAt` cannot separate two steps recorded in one millisecond: `sequence` is monotonic per run and `attempt` per `stepId`, both `UNIQUE`-constrained and both allocated in storage; an identical resend replays the same row while *different* content for a `stepId` becomes the next attempt, because §27 tracks retries and a retry is a second attempt. Runs and steps are **append-only** — no update or delete route, a closed run accepts nothing further, and re-closing never rewrites a verdict. The agent **version is pinned** from Phase 18's registry at open time, and a run opens only for an agent this workspace actually put in `production`, with Phase 19's evaluation gate unchanged and not bypassed. Seven workspace-scoped session-authenticated routes; forged `workspaceId`, `actorUserId`, `status`, `sequence`, `attempt` and timestamps are ignored. And the negative space, which is the point: **no runner, dispatcher, loop, scheduler, queue, worker, tool invoker, model client or network client is exported** — a `tool_call` step records that a tool was *reported* invoked and calls nothing, and the gate proves it by snapshotting every table. Phase 19's boundary is preserved: a trace writes no evaluation judgement and is never converted into one. |
| [0022 — Experiment Engine](./adr/0022-experiment-engine.md) | `@dealora/experiment` domain, `experiments` + `experiment_arms` + `experiment_events` (schema v19): `ROADMAP.md` §29's controlled experiments are split along the declared/derived line — storage holds only the declaration (which immutable drafts, on which metric, over how many days), the two-to-four pinned arms (`UNIQUE(experiment, position)`, `UNIQUE(experiment, draftId)`, and a `draftId` deliberately without a foreign key so an arm survives its draft's archive) and the append-only `created/started/closed/cancelled` trail with `CHECK`-constrained status↔timestamp agreement pairs, while **every tracked number is derived on read** — no column stores a sample, rate, confidence, total or winner, so nothing can go stale. §29's critical rule is enforced as published arithmetic, not mood: `positive_reply_rate` is the only metric (conversions read from Phase 12 through Phase 13's own `MEETABLE_INTENTS`, so "positive" cannot drift from a meeting recommendation), the population is accounts whose **newest** qualification is `qualified` (Phase 15's and Phase 16's shared rule, re-derived each read), exposure is a Phase 11 `sent` action inside a window that is the declared start plus declared duration capped by a close — **never a clock** — cost per arm is Phase 16's own `deriveBreakdown` over the arm's `outbound_send` facts, and revenue impact is **refused** (`revenue_per_arm` refused by name with Phase 23 as its owner; `revenueImpactMinor` is `null` with a reason, and the reported revenue-adjacent outcome is meetings on a calendar). The thresholds that make "do not claim a winning experiment when evidence is insufficient" decidable are published product judgements — 30 minimum sample per arm, 200 bp minimum lift, `medium` at 3×, `high` at 10× — decided by cross-multiplication in exact integer basis points with position as tiebreak, so an exact tie is `no_material_difference`, below-sample is `insufficient_evidence` with the reason, and a **cancelled** experiment can never crown. A contact reached by two arms inside the window is excluded from both and disclosed in `excludedCrossArmContacts` rather than averaged. Nine workspace-scoped routes (declare, read complete with comparison, list, pin arm, start, close, cancel, trail, policy); forged `status`, timestamps, identity, position and metric readings in a body are ignored. And the negative space, which is the point: no sender, no approver, no scheduler, no automatic assignment, no monetary revenue figure, no client-chosen arm, and the loop itself untouched — the experiment measures the revenue loop; it does not drive it. |

## Conventions

- Phase status and the next required slice are tracked in `ROADMAP.md`;
  update the roadmap when a phase gate is met.
- New environment keys are documented in `CONTRIBUTING.md` as they are
  introduced by the corresponding phase; secrets are never committed.
- Phase status is summarized in `README.md`; when a phase gate is met, update
  both so the roadmap and the overview agree.
- Public module interfaces carry doc comments; decisions that shape the
  architecture get an ADR.
- The four states of an agent stay distinct: **declared** (Phase 18's rule
  table), **evaluated** (Phase 19's stored judgements meeting every declared
  threshold), **production-eligible** (a person moved it, only if evaluated) and
  **executing** (does not exist in this repository). Never write a claim about
  one of these that belongs to another.
